Design System:
Scaling and Localizing the US Team’s Design System for Japan

How I evolved an inconsistent early design phase into a foundational design system tailored for the Japanese team.

Background

In the early stages of the Asurion Home+ project, we were tasked with localising a comprehensive US design system. While the system offered a strong foundation, it wasn’t directly compatible with the evolving requirements of the Japanese market.

After the first development phase, two of my design teammates left. With a New Year pause approaching and key teammates departing, I took the opportunity to consolidate our design work, resolve inconsistencies, and build a foundation that would support incoming team members.

Problems in Initial Design Phases

During Phase 1, each designer loosely followed the US style guide while also making quick, unsystematic adaptations to meet fast-changing needs. This approach led to inconsistencies and made alignment difficult.

  1. No Contextual Variables

    The U.S. design system lacked the contextual variables needed to efficiently manage colour in a new environment. Text styles didn’t translate well either—Japanese typography and layout rules required a different approach.

  2. Variable Inconsistencies

    While working on our own sections of the app, we had to quickly interpret how to use certain colours and spacing values. This produced inconsistencies as we neared the end of the phase and began aligning more closely.

System Foundations

With experience as both a designer and developer, I understood how crucial variables are for scalability—not just for speed, but for clarity between design and code. But I also know they serve different purposes: designers need clear context and an understanding of what's available, while front-end developers need structured tokens and predictability to avoid second-guessing how to define values in their CSS.

"Tokens and variables aren't just technical details—they're the foundation of a strong design-dev partnership."

Color Tokens and Variables

  • Reduced the broad US colour set into a smaller, more manageable token list, while referencing the original naming convention so it would still align with the dev team's codebase.
  • Integrated client modes into these colours, making it easier to create client screen versions by toggling the screen mode.
  • Applied these tokens contextually as colour variables at a small scale—covering text, surfaces, borders, and icons.

Typography

  • Added font family modes to enable screen-level font switching.

Issues: rem sizing isn’t directly supported in Figma, requiring documentation to map styles to CSS root values.

Breakpoints: Sizing & Spacing

  • Built a responsive system with breakpoints for adaptable screens.
  • Defined spacing, typography, and padding values at each breakpoint.

Issues: ghost modes may persist after syncing, creating confusion in handoff.

Text Styles

  • It’s a great moment to be intentional about how you define bold fonts for headings and body styles.
  • H1~H4 and standard text styles are universal, but I found each designer has their own way of labelling smaller body text—such as callout, note. It’s important to align as a group since this is a context designers will use daily.

Issues: Line-height and letter-spacing can’t be tokenised as percentages in Figma.

System Impact

By organising and structuring these variables, we had a system in place which—after aligning with the dev team—created a set of CSS root variables that could be applied to the web app with multiple client instances.

This gave developers a streamlined, consistent foundation to work from, making implementation smoother. Applying these variables across all screen UIs was a challenging task, but it ultimately eliminated inconsistencies, ensured cohesive design implementation, and improved collaboration between design and development teams.

Interface Design

Screen Templates

Creating specific breakpoint UI wasn’t possible early on, but became a priority once dev syncing increased. I also supported the QA team with early design inspection—flagging visual inconsistencies that can sometimes go unnoticed.

I enjoyed this part of the process. It came together smoothly by setting fixed screen widths per breakpoint, then applying template spacing—body, columns, rows—based on those values. Paired with responsive text styles, this approach gave us clean, reliable templates.

Issue: Figma doesn’t support percentage widths, so if layout columns change, each breakpoint needs its own screen. The upside is that this doubles as documentation.

Component Development

I built out the desktop components ahead of two new designers joining. The goal was to set up something clean and scalable, so they could slot in and start contributing without friction.

Component ownership was shared—each designer looked after their slice of the app. That structure kept things moving, encouraged accountability, and made it easier to grow the system without it falling apart. The early groundwork gave us a foundation to align on patterns and evolve them together.

Note Using sectioned components and avoiding inline UI makes Dev Mode’s version comparison tools far more effective. It ensures cleaner diffs, clearer history, and easier validation during handoff.

Userflow

Early on, handoff was split across multiple phased files, which made it tricky to track the latest screen versions and increased the risk of misalignment as the product grew.

From past experience, I knew that keeping one central userflow was key. It gives everyone—design, TA, QA, dev—a shared overview of all screens, and latest changes. It also gave me, and the other designers, a reliable space stay aligned on design intent.

  • I used Figma auto layout to define sections and screen flows, allowing the structure to grow and adapt without excessive manual rework.
  • Instead of resource-heavy flowline widgets, I overlaid FigJam arrows framed across the screen groups. Sectioning meant I could move arrows in groups, keeping the flow lightweight and manageable.

Handoff

Defining handoff rules led to some healthy back-and-forth, as each project had its own habits. I leaned toward a central sprint handoff file, with ideation staying in section-specific files like enrollment, login, and myPortal. In the end, we made those section files the main handoff locations. While it meant more Figma links to manage for external teams, it gave designers clearer ownership over their areas.

Each file had three main parts: dev-ready, in-progress, and exploration. This structure made it easier for others to understand both where things stood and how they were evolving.

Note: To get the most out of Dev Mode, it's important to clearly assign screens as 'ready for dev' and ensure they’re built using components.

Dev Alignment

A closer look at Dev Mode

As part of an initiative to strengthen the design-to-dev handoff, I integrated Figma's Dev Mode more intentionally into our shared workflow. It quickly surfaced gaps in our current process—from version control to inconsistent component usage—and revealed that Dev Mode offered far more than just inspection tools.

I began to introduce key features like:

  • Compare

    enabled version tracking of handoff-ready screens, helping teams validate updates without manual comparisons.

  • Component Playground

    provided developers and QA with a live preview of all component variants, bridging gaps between design intention and actual implementation.

This approach improved transparency across handoff touchpoints and helped build better alignment between design and engineering.

Outcome

It's in the Details

The careful attention to these small details meant our design vision was much more accurately realised in the final product. And perhaps most importantly, developers didn't face unnecessary friction, ensuring a collaborative and efficient process from start to finish. It also freed the design team to focus more on problem-solving and UX, rather than getting bogged down by visual design details.

Next Actions

I plan to deepen my understanding of how to connect design systems into tools like Storybook. Specifically, I want to explore how to link Figma tokens or component documentation with live components in Storybook.

Takeaways

  • Section Components Hold Up the System

    Section components allow you to scale with more confidence, while maintaining traceability across updates. They create clear units of UI that are easier to version, inspect, and test—especially when integrated with dev mode and component libraries.

  • Concise Style Variables Aid Creation

    Using a smaller set of well-defined variables helped limit inconsistencies and supported more deliberate design decisions. This encouraged designers to focus on intent and hierarchy, rather than surface-level tweaks.
